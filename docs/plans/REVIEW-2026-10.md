# Plan: `mgl review`, a trust layer for humans checking an agent's edit (2026-10-07)

Status: **proposed**, waiting for the owner. Nothing below is built yet except one additive SDK method
(`Project.historyEntries()`), which is easy to drop.

## The problem

Everything in Michelangelo so far serves the agent: one-line entities, ≤ 40-line output, contact sheets. The
human who asked for the video gets an `.mp4` and a chat summary. To trust it they must either watch the whole
video again after every round, or believe the agent's summary. Neither scales, and the second is exactly the
thing that should not be needed.

Trust comes from **inspectability** (I can see what was done) and **diff** (I can see what changed, against a
state I already accepted). Simple beats clever: one command, one page, read top to bottom in under a minute.

## What Claude Code does to earn trust, and what we take from it

| Claude Code | Why it creates trust | Michelangelo today | `review` adds |
|---|---|---|---|
| **Every edit is shown as a diff** before or as it lands (red/green lines in the prompt, or the IDE's diff view) | you judge the change, not the claim | `edit` prints ≤ 10 changed lines; `--dry-run` | a field-level diff (`y: 420 → 380`) and the raw file diff, for all steps at once |
| **Every action is visible** in the transcript (commands run, files read, outputs), collapsed but expandable | nothing happens off-screen | `.mgl/<p>/history.json` records each step's commands, but nobody reads it | the steps as a numbered log: what the agent ran, in order, with what each step changed |
| **Checkpoints and rewind** (Esc Esc, `/rewind`) make any step cheap to undo | low cost of being wrong → willing to let it act | `edit undo [n]` across processes | each step names its undo command; `--approve` makes a checkpoint to compare against next time |
| **Permission modes / plan mode**: approve before acting, then grant more autonomy as trust grows | a human gate where it matters, none where it doesn't | none | `--approve` is the gate: "this is the state I accepted"; later reviews show only what changed since |
| **Clickable `file:line` references** | claims point at evidence | errors and `show` print line numbers | every change carries its line (`L14`) in the project file |
| **Honest summaries**: says what failed, what was skipped, what was verified | the summary is checkable, so it gets believed | QA findings with fixes | QA compared before/after: fixed, new, still open; never hidden |
| **Plain files in git** (no hidden state, commits attributed) | the ground truth is inspectable with tools you already have | the project file is the truth (R2) | the page shows the file diff, the same thing `git diff` would |

What we do **not** take: per-change approval prompts (too slow for a 60-clip edit) and a live UI (R6: no
browser in the package; the page is a static file a human opens).

The one thing video needs that code does not: **pictures**. A code diff is the change; a video diff must also be
*seen*. So the page leads with before/after frames and a pixel diff of exactly the moments that changed.

## The design

```
mgl review <file> [--approve] [--steps n] [--against old.mgl.json] [-n 6] [--comp id] [-o review.html]
```

One verb, three outputs, from most portable to most detailed (see "Where humans see it" below):

1. **Text** (stdout, ≤ 8 lines, valid Markdown): the summary the agent relays in chat. Works in any terminal or
   chat.
2. **Review card** (`.mgl/<p>/review/card.png`, long edge ≤ 1568 px): one image with the verdict, up to 3
   before · after · changed rows and the timeline. One image goes everywhere: an app's side panel, a PR, a
   message. The agent can also `Read` it (R5), so the agent and the human check the same picture.
3. **Page** (`.mgl/<p>/review/index.html`, self-contained, no scripts): everything, for a closer look.

```
**review** 4 steps since you approved (14:02) · 6 changes · 0 not from a recorded step · QA 1 fixed, 0 new, 2 open
frames: f45 12% changed · f120 4% · f300 no change
| # | step | changed |
|---|---|---|
| 1 | `clip.set title y=380` | title: y 420 → 380 |
| 2 | `motion.apply title in=pop` | title: animate + in pop |
card: .mgl/video/review/card.png · page: .mgl/video/review/index.html
approve: `mgl review video.mgl.json --approve` · undo steps 2..4: `mgl edit video.mgl.json undo 3`
```

### What it compares against (the baseline), in this order

1. `--against old.mgl.json`: any other version (e.g. `git show HEAD:video.mgl.json > old.mgl.json`).
2. `--steps n`: the state before the last n recorded steps (history patches applied in reverse).
3. The **last approved state** (`.mgl/<p>/review/approved.json`, written by `--approve`). The default once a
   human has approved anything: "show me what changed since I last looked".
4. Otherwise the start of recorded history (all steps that still reverse cleanly; it says when it stops early).

With an approved snapshot, a change no recorded step explains (a hand edit, another tool) is shown in its own
orange group: **"not from a recorded step"**. That is the part a human most needs to see, and the history alone
cannot reveal it.

### The page, top to bottom (each section answers one question)

1. **Verdict bar**: baseline, steps, changes, unexplained changes, frames visibly changed, QA fixed/new/open.
   Green when nothing is new or unexplained, amber otherwise. *Should I worry?*
2. **Look**: for each moment that changed, three images side by side: before · after · changed pixels
   (magenta on a dimmed frame, with the changed area boxed and the % changed). Labelled with time, frame and the
   clips there. *Is it what I asked for?*
3. **Timeline**: one row per track; clips grey if unchanged, green added, amber changed (dashed ghost where it
   was), red dashed removed; the compared frames marked. *Where in the video did it act?*
4. **Changes**: one card per changed entity, `clip "title" L14`, fields `y: 420 → 380`, tagged with the steps
   that made it. Adds and removes show the whole line. *What exactly changed?*
5. **Steps**: the agent's log, numbered, with time, summary, the commands (collapsed) and the undo command
   (`mgl edit video.mgl.json undo 3` reverts steps 3..n). *What did it do, and can I take it back?*
6. **QA**: fixed / new / still open, with each finding's fix. *Did it break anything it knows about?*
7. **File diff** (collapsed): the unified diff of the project file, the ground truth.
8. **Footer**: how to approve, how to undo.

Frames are chosen from the changes, not evenly: the middle of each changed visual clip (before and after spans),
each changed cue, plus 3 even frames when a style, track, comp or the project changed. At most 6, deduplicated.
Sound-only changes render one frame to show "no picture change" and list the sound fields. If the comp size
changed, the pixel diff is skipped and says why. Render scale keeps tiles ≤ 640 px tall (≈ 1 s for 6 frames).

## Where humans see it: Claude Code and Codex

The human does not open Michelangelo. They watch Claude Code or Codex work. So `review` adds no UI of its own;
it produces evidence that each host already knows how to show, and the agent's instructions say when to show it.

**The review card:**

```
┌───────────────────────────────────────────────────────────────────────┐
│ ● 4 steps since approved · 6 changes · 0 unexplained · QA 1 fixed 0 new │  green / amber
├─────────────┬─────────────┬─────────────┬─────────────────────────────┤
│   before    │    after    │   changed   │ 1.50s f45 · title, shot2    │
│   [frame]   │   [frame]   │ [magenta]   │ 12% of pixels               │
├─────────────┼─────────────┼─────────────┼─────────────────────────────┤
│   … up to 3 rows, the frames that changed most                        │
├───────────────────────────────────────────────────────────────────────┤
│ V1 ▇▇▇▇▇▇[▇▇▇]▇▇▇▇   T1 ░░[▇▇]░░░   A1 ▇▇▇▇▇▇▇▇▇     ▲1  ▲2  ▲3     │  timeline
└───────────────────────────────────────────────────────────────────────┘
```

**How each host shows it:**

| Surface | What the human sees | How |
|---|---|---|
| Claude Code, terminal | the Markdown summary in the transcript; the card and page as paths to open | the agent ends a round with `mgl review` and relays its output |
| Claude Code, desktop / web / mobile app | the card inline in the side panel, with the page one tap away | the agent sends `card.png` (and `index.html`) to the user as files |
| Claude Code, IDE extension | the project file diff in the editor's diff view | direct edits to the one-entity-per-line file already show as native diffs |
| Codex CLI | the summary in the final message; the card and page as paths to open | instruction in `AGENTS.md` (same wording as SKILL.md) |
| Codex cloud / any PR | the `.mgl.json` diff in the PR (readable: one entity per line), with the summary and card in the description | the agent pastes the summary; the card goes in when the host can attach images |

**What the hosts already give us, for free:**

- **Native diffs.** When an agent edits `video.mgl.json` with its file-edit tool, both hosts show a red/green diff
  of the changed lines, because the format keeps one entity per line (R1). `review` covers what those diffs
  miss: the pixels, and changes made through `mgl edit` (which reach the file through a shell command).
- **Readable commands in approval prompts.** When the host asks permission to run a command, the human reads
  `mgl edit video.mgl.json clip.set title y=380`. The `k=v` form is already plain enough to approve on sight;
  keep it that way (no opaque JSON blobs in prompts when `k=v` will do).
- **Approval in conversation.** The human types "looks good" and the agent runs `--approve`, or "undo the
  last two" and the agent runs `edit undo 2`. No new buttons.

**When the agent shows it (one line in SKILL.md and AGENTS.md):** "After a round of edits and before you say
you are done, run `mgl review <file>`, look at `card.png` yourself, then give the human the summary and the
card. Never claim a change you cannot point to on the card or in the summary."

**Later, if wanted (not in this build):** a Claude Code hook that runs `mgl review --brief` at the end of
every turn that touched a `.mgl.json`; a status line reading `mgl: 4 unapproved changes`; the same as a Codex
notify hook where Codex supports one.

## Decisions for the owner

- **(Ask) A tenth verb.** DESIGN R3 and the README say nine. `review` is for humans, not the agent, so it earns
  its own name; the alternative is `look --review`. Recommended: a tenth verb.
- **(Ask) Gate renders on approval?** E.g. `render --final` notes "4 unapproved changes (mgl review)". Off in this
  plan; easy to add later, the way Claude Code grants more autonomy as trust grows.
- **(R) Review a proposal before it is applied** (`review --batch edits.jsonl`, like plan mode): later, once the
  page has been used on real edits.
- **(R)** Snapshot and page live in `.mgl/<p>/review/`, already git-ignored.
